## Abstract

This RIP specifies a transaction-version replay-protection mechanism for Rincoin. From the RinHash fork height (Block 840,000 on mainnet), every non-exempt transaction included in a block MUST carry `nVersion = 0x52494e33` (ASCII "RIN3", big-endian = 1,380,535,859). The marker version places RinHash identity in the transaction body, so that a transaction without it, such as one built for a pre-fork chain, cannot be mined onto the post-fork chain. The protection is one-directional by construction, and it does not separate the post-fork chain from a chain that requires the same marker (see Motivation and Security Considerations); the sighash algorithm itself is unchanged.

Enforcement is applied across three independent layers — consensus, mempool admission, and block assembly — to close a denial-of-service vector not addressed by the cited commit from which the RIN3 constant is adopted. Mempool rejections are classified as recent-consensus-change so that honest peers relaying pre-fork transactions at the activation boundary are not discouraged (§3 Layer 2).

---

## Motivation

Rincoin descends from Bitcoin → Litecoin → Rincoin. Transactions valid on a pre-fork chain, or on a chain that shares Rincoin's UTXO history, could otherwise be replayed onto the post-fork chain. Requiring a distinct `nVersion` marker makes a transaction that lacks the marker invalid under Rincoin consensus from the fork height, so it cannot be mined onto the post-fork chain. The marker separates the post-fork chain only from chains that do not also require `0x52494e33` (see Security Considerations).

**The protection is one-directional, and the asymmetry is a property of the mechanism rather than a gap in its implementation.** `nVersion` is part of the transaction body and therefore of the sighash preimage, but both chains compute that preimage the same way over the same bytes: a marker-versioned transaction replayed onto a chain that does not require the marker carries the same bytes, hashes to the same value, and its signatures remain valid there. What limits that direction is relay policy rather than consensus: a RIN3-unaware node's `IsStandardTx` treats the marker version as non-standard, so with standardness enforced, as it always is on mainnet, the node neither accepts nor relays the transaction; yet a block that contains it is valid for that node (both measured; see Security Considerations and Verification). A rule that only narrows validity cannot do better, because every transaction valid under it is also valid under the rules it narrows. Two-way protection needs a change that makes post-fork transactions invalid under the old rules, in the `SIGHASH_FORKID` sense by altering the sighash algorithm itself, and this RIP deliberately does not make one: the consensus change is one constant and one height-gated rule, with no new signature format and no change to how wallets sign.

## Specification

### 1. Constant

```cpp
// src/primitives/transaction.h, class CTransaction
static const int32_t RIN_FORK_TX_VERSION = 0x52494e33; // "RIN3" BE = 1380535859
```

The decimal value is **1,380,535,859**. Implementations MUST use this exact value. An implementation built with a different value rejects every post-fork block that carries a correctly marked non-exempt transaction, and conforming nodes reject the transactions its wallet builds: a consensus split. Signatures are unaffected; they commit to whatever `nVersion` the transaction carries and verify the same way on every node.

---

### 2. Activation Height

| Network | `nRinHashForkHeight` | Relation |
|---------|---------------------|----------|
| Mainnet | 840,000 | 4 × `nSubsidyHalvingInterval` (210,000) |
| Testnet | 840 | 4 × 210 |
| Regtest | 840 | 4 × 210 |

RIN3 activates at the **same height as the Customized Halving hard fork (RIP-0002)**. Consolidating all consensus changes into a single fork event at Block 840,000 minimizes operational disruption for node operators and mining pools.

`nRinHashForkHeight` MUST equal 4 × `nSubsidyHalvingInterval` on every network. The two values are set in separate `Consensus::Params` fields, and the functional test suite exercises the relation only at regtest scale; height 840,000 is not reachable by a functional test. Implementations MUST therefore assert the relation in every `CChainParams` constructor they define, alongside the genesis and merkle-root assertions such constructors already carry. A mismatch yields a network on which the Customized Halving dilation and RIN3 enforcement activate at different heights: at regtest scale the RIN3 functional tests fail wholesale, a symptom a long way from its cause; at mainnet scale nothing fails until the fork height is reached in production.

---

### 3. Enforcement Layers

A transaction is *exempt* if it is a coinbase, a HogEx transaction, or an MWEB-only transaction. For every non-exempt transaction at effective height `h >= nRinHashForkHeight`, `nVersion` MUST equal `RIN_FORK_TX_VERSION`.

*(Layer numbers here are ordered by authority. The commit message of `51ad19b` numbers the same layers in pipeline order, mempool first; `9426ca3` follows the numbering of this RIP.)*

**Layer 1 — Consensus (`ContextualCheckBlock`, `validation.cpp`):** A block containing any non-exempt transaction whose `nVersion` is not `RIN_FORK_TX_VERSION` at `h >= nRinHashForkHeight` is rejected with `bad-tx-rinhash-version` (`BlockValidationResult::BLOCK_CONSENSUS`). This is the authoritative consensus rule.

**Layer 2 — Mempool admission (`MemPoolAccept::PreChecks`, `validation.cpp`):** A transaction submitted via `sendrawtransaction` or relayed to the mempool, where the next block height (`ChainActive().Tip()->nHeight + 1`) is `>= nRinHashForkHeight`, is rejected with `bad-tx-rinhash-version` if it is non-exempt and lacks the marker version. MWEBOnly is exempt, consistent with Layer 1. The rejection MUST be classified as `TxValidationResult::TX_RECENT_CONSENSUS_CHANGE`, not `TX_CONSENSUS`: RIN3 is a consensus rule more recent than SegWit, and `MaybePunishNodeForTx` assigns `TX_CONSENSUS` a misbehavior score of 100 (instant discouragement), whereas `TX_RECENT_CONSENSUS_CHANGE` carries no score. A pre-fork legacy transaction lingering in an honest node's mempool across the boundary, or relayed by a non-upgraded node passively following the post-fork chain, must not cause the relaying peer to be discouraged; the transaction is still rejected and never mined. Layer 1 retains `BLOCK_CONSENSUS` (see Security Considerations).

**Layer 3 — Block assembly (`BlockAssembler::TestPackageTransactions`, `miner.cpp`):** Belt-and-suspenders skip. If a legacy-`nVersion` transaction reaches the block-assembly package despite Layer 2, it is skipped (`return false`) so `CreateNewBlock` never emits an invalid block.

---

### 4. Relay Standardness

`IsStandardTx` (`src/policy/policy.cpp`) MUST accept `RIN_FORK_TX_VERSION` as a standard transaction version, in addition to the legacy standard range. Without this rule, every marker-versioned transaction would be rejected as a non-standard `version` wherever standardness is enforced, which on mainnet is always: every post-fork transaction, and those the wallet builds while the tip is at `nRinHashForkHeight - 1` (§5). This is a permissive relay-policy (standardness) rule with no consensus effect; it is not a fourth enforcement layer.

---

### 5. Wallet Behaviour

`wallet/txassembler` sets the outgoing transaction `nVersion` from the height of the last block the wallet has processed (`GetLastBlockHeight()`, normally the chain tip) at construction time:

```
if (last_height >= nRinHashForkHeight - 1)  // = 839 on regtest
    nVersion = RIN_FORK_TX_VERSION;
// otherwise nVersion keeps its default, 2
```

The `- 1` offset ensures a transaction constructed while the tip is at `nRinHashForkHeight - 1` is already marker-versioned, so that it remains valid when mined into the fork block itself, avoiding a race at the boundary.

---

### 6. P2P Deployment

Nothing in this section is a consensus rule; it governs peer discovery and telemetry for the RIN3 rollout.

**Service bit.**

```cpp
// src/protocol.h
NODE_RIN3 = (1 << 25)
```

`NODE_RIN3` signals that the node enforces this RIP and accepts and relays `RIN_FORK_TX_VERSION` transactions. It is advertised unconditionally from Rincoin Core v1.1.0 and rendered as `"RIN3"` in `getnetworkinfo`/`getpeerinfo` service names. This follows the capability-bit pattern of SegWit (`NODE_WITNESS`) and Litecoin MWEB (`NODE_MWEB`), the only comparable consensus changes in the lineage that required P2P support. Bit 25 is not assigned in either upstream lineage, but it lies in the range both reserve for temporary experiments (Bitcoin Core: bits 24–31; Litecoin: bits 25–31, with bit 24 assigned to `NODE_MWEB`); Rincoin Core narrows its own reservation to bits 26–31. Service bits are unauthenticated advertisements, so a collision would be silent.

**Outbound service requirement.** `GetDesirableServiceFlags` (`src/protocol.cpp`) MUST include `NODE_RIN3`. Automatic outbound connections are then made only to addresses recorded as advertising `NODE_RIN3`, and an automatic outbound connection (full-relay, block-relay-only or addr-fetch) to a peer that does not advertise it is dropped during the version handshake; there is no fallback to legacy peers. A RIN3-unaware node's `IsStandardTx` rejects marker-versioned transactions as non-standard `version` (its `MAX_STANDARD_VERSION` is 2): post-fork transaction propagation therefore depends entirely on the upgraded-node subgraph being connected, and this requirement is what guarantees that connectivity. Inbound, manual (`-addnode`, `-connect`) and feeler connections are exempt, so legacy nodes can still connect to upgraded nodes and keep following the chain, preserving the soft-fork property.

**Protocol version (telemetry only).** `PROTOCOL_VERSION` is raised to 70018 so that `getpeerinfo` and seeder crawls can measure the RIN3-capable share of the network ahead of activation — the quantitative input for the Block 840,000 go/no-go decision. Capability detection itself uses `NODE_RIN3`, never the version number.

**No version floor.** `MIN_PEER_PROTO_VERSION` remains 31800; a floor of 70018 is permanently not adopted (see Rationale 6). No peer at or above that inherited floor, which every Rincoin release exceeds, is disconnected on account of its protocol version.

**Rollout ordering.** Because `GetDesirableServiceFlags` also feeds the DNS-seed service filter, v1.1.0 nodes ask the DNS seeders for `x3000009`. Before public binaries ship, the DNS seeders MUST accept that filter, and the official nodes MUST run v1.1.0 so that the seeders have `NODE_RIN3` nodes to return; otherwise early adopters' automatic outbound selection finds no `NODE_RIN3` peers. A DNS seeder is a separate crawler and does not itself run Rincoin Core. Manual `-addnode` to an official node is the documented fallback.

## Rationale

### Improvements Over the Cited Commit

1. **Mempool Zombie DoS prevention (original).** The cited commit describes only consensus-layer enforcement and relay standardness. It does not address a denial-of-service vector in which a high-fee legacy-`nVersion` transaction is admitted to the mempool, is then selected by the block assembler, and makes `TestBlockValidity` fail inside `CreateNewBlock`, which then throws — stalling block production for as long as the transaction lingers (up to the mempool expiry). Layer 2 closes this by performing a height-aware rejection at mempool entry; Layer 3 provides defence in depth.

2. **CH-integrated single hard fork (original).** The cited commit positions its era at Block 630,000 (3 × halving interval). This RIP positions RIN3 at Block 840,000 (4 × halving interval) so that it activates simultaneously with the Customized Halving dilation (RIP-0002), presenting node operators and pools with a single, well-announced fork event.

3. **Scope reduction (governance decision).** The cited commit introduces a general init+overlay era table covering PoW parameters, a coinbase OP_RETURN marker, the fork tx version, and a peer-protocol floor, driven by a generated C++ header from JSON. The Core Strategic Authority (CSA) evaluated the full era system and did not adopt it. This RIP extracts only the RIN3 nVersion rule; the OP_RETURN `RIN1` branding marker is deferred (optional, no consensus impact), and the peer-protocol floor is not adopted — redesigned as `NODE_RIN3` capability signaling (§6, Rationale 6).

   **PoW parameters are out of scope and unchanged.** The era table would render RinHash PoW parameters (Argon2d `t_cost`, `m_cost`, `lanes`, `salt`) changeable as configuration data, including a reserved `"PENDING"` salt slot for overlays not yet committed. This mechanism is not adopted. RinHash PoW parameters are consensus parameters: any change to them requires its own RIP, ratification under RIP-0001, and network adoption — the same bar as any other hard fork. Neither this RIP nor any parameter table shipped with the implementation authorises, or pre-authorises, a change to RinHash PoW parameters.

4. **Attack-simulation verification (original).** Customized Halving subsidy determinism is exercised across reorgs of up to 5,461 blocks (1/1000 scale) that erase the entire post-CH history (`sim-ch-attack.sh`, which contains no RIN3 checks). The wallet's RIN3 version switch at the fork boundary is exercised by `sim-ch-rin3.sh`, including after the tip is rolled back across the boundary, and the enforcement layers by `feature_rin3_enforcement.py`. See the Verification section.

5. **Peer DoS-score classification (original).** The cited commit does not address peer punishment semantics. Layer 2 rejections are classified `TX_RECENT_CONSENSUS_CHANGE` rather than `TX_CONSENSUS`, using the bucket Bitcoin Core reserves for rules newer than SegWit. With `TX_CONSENSUS`, every relay of a legacy transaction after the fork would score the relaying peer 100 points — instant discouragement. Because `recentRejects` is reset on every chain-tip change and Rincoin's block interval is 60 seconds, that filter provides only ~1 minute of repeat-suppression, so honest v1.1.0 nodes holding pre-fork mempool residue, and non-upgraded nodes passively following the post-fork chain, would be progressively disconnected from the network. The classification keeps rejection (and the Mempool Zombie DoS defence) fully intact while removing the punishment. Non-upgraded peers are not disconnected for relaying legacy transactions (this classification) or for their protocol version (a floor is permanently not adopted; §6, Rationale 6). Upgraded nodes instead make their automatic outbound connections only to `NODE_RIN3`-capable peers, while non-upgraded peers can still connect to them inbound.

6. **Capability signaling instead of a version floor (redesign).** The cited commit's peer-protocol floor — a minimum peer version of 70018 — was evaluated by the Core Strategic Authority and permanently not adopted, for three reasons: a version floor disconnects legacy peers that would otherwise keep following the chain, manufacturing the very partition the fork design avoids; a self-reported protocol version is no defence against a hostile fork; and the Bitcoin Core lineage has never raised `MIN_PEER_PROTO_VERSION` across BIP65, CSV, SegWit, or Taproot. The deployment need the floor was meant to serve — upgraded nodes finding RIN3-capable relay peers — is met instead by the `NODE_RIN3` service bit with the outbound service requirement (§6), the mechanism used by the only comparable consensus changes in the lineage (SegWit `NODE_WITNESS`, Litecoin MWEB `NODE_MWEB`). The protocol-version bump to 70018 is retained as telemetry only. This entry records both the disposition of the cited commit's idea and the redesign that replaced it.

## Backwards Compatibility

This is a hard fork with respect to the bundled Block 840,000 event (RIP-0002 + this RIP). In isolation, the RIN3 rule narrows the block-validity set (a consensus tightening): legacy consensus places no constraint on transaction `nVersion`, so nodes that enforce Customized Halving but not RIN3 accept the post-fork chain. Before `nRinHashForkHeight`, the rule is dormant and historical blocks validate unchanged. Wallets and services that construct raw transactions MUST set `nVersion = 1380535859` for transactions intended for inclusion at or after the fork height. As of `v1.1.0-rc1` this includes the node's own raw-transaction and PSBT paths: `createrawtransaction` with `fundrawtransaction`, and `walletcreatefundedpsbt`, leave `nVersion` at 2, and a transaction built that way after the fork height is rejected with `bad-tx-rinhash-version` (measured; see Verification). Only the wallet's own send path sets the marker (§5). Callers of those RPCs MUST set the version field themselves before signing, since `nVersion` is covered by the signature; `fundrawtransaction` preserves a version the caller has already set. Coinbase, HogEx, and MWEB-only transactions are unaffected.

Non-upgraded node populations diverge in two distinct ways at Block 840,000:

- **Pre-CH implementations** (original halving schedule) reject the post-fork chain itself: the Customized Halving subsidy (4 RIN at Block 840,000) violates their expected schedule, producing a hard divergence. Rincoin Core 0.21.4 (tag `v0.1.0`) is in this class: its `GetBlockSubsidy` halves every 210,000 blocks and expects 3.125 RIN at Block 840,000.
- **CH-aware, RIN3-unaware implementations** (Rincoin Core v1.0.6) accept and passively follow the post-fork chain, but cannot produce acceptable blocks containing legacy-version transactions, and their wallets emit legacy-version transactions that are unmineable on the post-fork chain — with their own wallets such nodes can receive but not spend, and they do not relay post-fork transactions.

Block 840,000 is therefore a hard fork relative to pre-CH implementations, while the rule in this RIP is a soft fork relative to CH-aware ones. Non-upgraded nodes that passively follow the post-fork chain and relay legacy-version transactions are not discouraged at the P2P layer for doing so (§3 Layer 2), and no protocol-version floor ever disconnects them (§6). Such nodes are relay-inert for post-fork transactions — their `IsStandardTx` rejects marker-versioned transactions as non-standard, as measured on a v1.0.6 build (Verification) — so post-fork propagation relies on the `NODE_RIN3` outbound requirement keeping the upgraded subgraph connected (§6).

## Security Considerations

- **One-directional protection.** The rule protects the post-fork chain: a transaction built for a legacy chain is rejected there by consensus (`bad-tx-rinhash-version`, §3 Layer 1). It does not protect a legacy chain against a marker-versioned transaction. Such a transaction carries the same bytes on both chains, so its signatures remain valid on the legacy chain, and only relay policy stands in the way. On mainnet a RIN3-unaware node always enforces standardness (`-acceptnonstdtxn` is refused there), and its `IsStandardTx` rejects the marker version as non-standard (its `MAX_STANDARD_VERSION` is 2), so the node neither accepts nor relays the transaction. Consensus does not stop it: a block that contains the transaction is valid for such a node, so a miner on a legacy chain who includes it (which requires bypassing the standardness check, for example with modified mining software) produces a block that legacy nodes accept. Both behaviours were measured on a Rincoin Core v1.0.6 build (see Verification). Exchanges, custodians and other services that continue to follow a legacy chain after the fork MUST NOT rely on the marker for replay safety in that direction, and should apply their own splitting measures.

- **Chains that share the marker.** The marker distinguishes the post-fork chain only from chains that do not also require `0x52494e33`. A chain that enforces the same value, for example one split from this rule set after the fork height, is not separated from this chain by the marker in either direction: a transaction valid on one is valid on the other wherever the outputs it spends exist on both.

- **Incorrect constant.** An implementation using the wrong value for `RIN_FORK_TX_VERSION` splits from conforming nodes at the first post-fork block that carries a non-exempt transaction (§1); if it has hashpower, the split can persist. Implementations MUST verify the constant is exactly `0x52494e33` = 1,380,535,859 and MUST include a test vector confirming this before deployment.

- **Mempool Zombie DoS.** With only Layer 1, a high-fee legacy-nVersion transaction can stay in the mempool and make `CreateNewBlock` fail on every attempt until the 14-day mempool expiry, denying block production. Layer 2 (height-aware mempool rejection) and Layer 3 (block-assembly skip) together eliminate this vector. Operators MUST deploy both layers; deploying only Layer 1 leaves the DoS window open.

- **Peer discouragement at the boundary.** Layer 2 MUST use `TX_RECENT_CONSENSUS_CHANGE`. With `TX_CONSENSUS`, a single legacy transaction relayed after the fork discourages the sending peer (score 100), and because `recentRejects` resets every 60-second tip change, the effect repeats: honest nodes with pre-fork mempool residue and non-upgraded passive followers would be severed from the P2P graph within hours of activation. The trade-off is that a peer can spam unique legacy transactions without accruing a misbehavior score; the cost is bounded by bandwidth, and the check is performed early in `PreChecks` (before signature validation), and this uses the classification Bitcoin Core reserves for post-SegWit consensus changes. Layer 1 (block-level) retains `BLOCK_CONSENSUS`: the compact-block relay path is already exempt from punishment (`via_compact_block`), and peers extending the legacy branch are disconnected regardless via `BLOCK_INVALID_PREV` on descendant blocks. The accepted cost is that a non-upgraded node which relays a block carrying a legacy transaction, mined by a non-upgraded miner, is still discouraged when that block reaches an upgraded node by full-block download rather than compact-block relay (manual and `noban` peers excepted).

- **Boundary race condition.** A transaction constructed at tip height `nRinHashForkHeight - 1` must already carry `RIN_FORK_TX_VERSION`, as it may be confirmed in the fork block itself. The `last_height >= fork - 1` offset in `txassembler` handles this. Wallet implementations that compute the version from the height of the block the transaction is intended for (tip + 1) MUST switch when that height is `>= nRinHashForkHeight`, which is the same condition.

- **Exempt transaction abuse.** The exemption sets MUST be equivalent in effect: a transaction exempt at one layer MUST be exempt at every layer at which it can appear. The layers need not share a literal predicate — Layer 1 tests coinbase, HogEx, and MWEB-only explicitly, because all three can appear in a block; Layers 2 and 3 test only MWEB-only, because coinbase and HogEx transactions are rejected earlier in `MemPoolAccept::PreChecks` and therefore never reach the mempool or the block-assembly package. Implementations that relax those earlier rejections MUST restore the coinbase and HogEx tests at Layers 2 and 3.

## Reference Implementation

In the Rincoin Core reference implementation, the constant is defined in `src/primitives/transaction.h` (§1); the activation heights and their invariant are in `src/consensus/params.h` and `src/chainparams.cpp` (§2); the enforcement layers are in `src/validation.cpp` (`MemPoolAccept::PreChecks`, `ContextualCheckBlock`) and `src/miner.cpp` (`BlockAssembler::TestPackageTransactions`) (§3); relay standardness is in `src/policy/policy.cpp` (`IsStandardTx`, §4); the wallet behaviour is in `src/wallet/txassembler.cpp` (§5); and the P2P deployment is in `src/protocol.h`, `src/protocol.cpp`, `src/init.cpp` and `src/version.h` (§6).

The complete change set is present in the signed tag [`v1.1.0-rc1`](https://github.com/Rin-coin/rincoin/releases/tag/v1.1.0-rc1), commit `a1b12dc8c332677c1fb8b3dbf32ca91f258f6d59`, on the `v1.1` branch of the canonical repository. That tag is a release candidate: canonical ratification follows the `v1.1` → `master` merge under RIP-0001.
