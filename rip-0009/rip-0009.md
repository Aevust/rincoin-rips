## Abstract

This RIP specifies a transaction-version replay-protection mechanism for Rincoin. From the RinHash fork height (Block 840,000 on mainnet), every non-exempt transaction included in a block MUST carry `nVersion = 0x52494e33` (ASCII "RIN3", big-endian = 1,380,535,859). The marker version embeds RinHash identity into every transaction's sighash preimage, providing fork-id-style replay protection against pre-fork and sibling chains without altering the sighash algorithm.

Enforcement is applied across three independent layers — consensus, mempool admission, and block assembly — to close a denial-of-service vector not addressed by the cited commit from which the RIN3 constant is adopted. Mempool rejections are classified as recent-consensus-change so that honest peers relaying pre-fork transactions at the activation boundary are not discouraged (§3 Layer 2).

---

## Motivation

Rincoin descends from Bitcoin → Litecoin → Rincoin. Transactions valid on a pre-fork chain (or on a chain that shares Rincoin's UTXO history) could otherwise be replayed on the post-fork chain. Embedding a distinct `nVersion` marker into the signed transaction body causes any signature produced for the post-fork chain to be invalid on chains that do not require the marker, and vice versa, achieving replay protection with a minimal, well-understood change surface.

## Specification

### 1. Constant

```cpp
// src/primitives/transaction.h
static const int32_t RIN_FORK_TX_VERSION = 0x52494e33; // "RIN3" BE = 1380535859
```

The decimal value is **1,380,535,859**. Implementations MUST use this exact value; an incorrect constant produces sighash divergence and a permanent chain split.

---

### 2. Activation Height

| Network | `nRinHashForkHeight` | Relation |
|---------|---------------------|----------|
| Mainnet | 840,000 | 4 × `nSubsidyHalvingInterval` (210,000) |
| Testnet | 840 | 4 × 210 |
| Regtest | 840 | 4 × 210 |

RIN3 activates at the **same height as the Customized Halving hard fork (RIP-0002)**. Consolidating all consensus changes into a single fork event at Block 840,000 minimizes operational disruption for node operators and mining pools.

---

### 3. Enforcement Layers

A transaction is *exempt* if it is a coinbase, a HogEx transaction, or an MWEB-only transaction. For every non-exempt transaction at effective height `h >= nRinHashForkHeight`, `nVersion` MUST equal `RIN_FORK_TX_VERSION`.

*(Layer numbers here are ordered by authority; the reference-implementation commit messages number the same layers in pipeline order, mempool first.)*

**Layer 1 — Consensus (`ContextualCheckBlock`, `validation.cpp`):** A block containing any non-exempt transaction whose `nVersion` is not `RIN_FORK_TX_VERSION` at `h >= nRinHashForkHeight` is rejected with `bad-tx-rinhash-version` (`BlockValidationResult::BLOCK_CONSENSUS`). This is the authoritative consensus rule.

**Layer 2 — Mempool admission (`MemPoolAccept::PreChecks`, `validation.cpp`):** A transaction submitted via `sendrawtransaction` or relayed to the mempool, where the next block height (`ChainActive().Tip()->nHeight + 1`) is `>= nRinHashForkHeight`, is rejected with `bad-tx-rinhash-version` if it is non-exempt and lacks the marker version. MWEBOnly is exempt, consistent with Layer 1. The rejection MUST be classified as `TxValidationResult::TX_RECENT_CONSENSUS_CHANGE`, not `TX_CONSENSUS`: RIN3 is a consensus rule more recent than SegWit, and `MaybePunishNodeForTx` assigns `TX_CONSENSUS` a misbehavior score of 100 (instant discouragement), whereas `TX_RECENT_CONSENSUS_CHANGE` carries no score. A pre-fork legacy transaction lingering in an honest node's mempool across the boundary, or relayed by a non-upgraded node passively following the post-fork chain, must not cause the relaying peer to be discouraged; the transaction is still rejected and never mined. Layer 1 retains `BLOCK_CONSENSUS` (see Security Considerations).

**Layer 3 — Block assembly (`BlockAssembler::TestPackageTransactions`, `miner.cpp`):** Belt-and-suspenders skip. If a legacy-`nVersion` transaction reaches the block-assembly package despite Layer 2, it is skipped (`return false`) so `CreateNewBlock` never emits an invalid block.

---

### 4. Relay Standardness

`IsStandardTx` (`src/policy/policy.cpp`) MUST accept `RIN_FORK_TX_VERSION` as a standard transaction version, in addition to the legacy standard range. Without this rule, a marker-versioned transaction constructed while the tip is at `nRinHashForkHeight - 1` (§5) would be rejected at relay as a non-standard `version` before the fork block is mined, breaking the wallet boundary behaviour. This is a permissive relay-policy (standardness) rule with no consensus effect; it is not a fourth enforcement layer.

---

### 5. Wallet Behaviour

`wallet/txassembler` sets the outgoing transaction `nVersion` based on the chain tip at construction time:

```
if (last_height >= nRinHashForkHeight - 1)  // = 839 on regtest
    nVersion = RIN_FORK_TX_VERSION;
else
    nVersion = legacy;
```

The `- 1` offset ensures a transaction constructed while the tip is at `nRinHashForkHeight - 1` is already marker-versioned, so that it remains valid when mined into the fork block itself, avoiding a race at the boundary.

## Rationale

### Improvements Over the Cited Commit

1. **Mempool Zombie DoS prevention (original).** The cited commit describes only consensus-layer enforcement and relay standardness. It does not address a denial-of-service vector in which a high-fee legacy-`nVersion` transaction is admitted to the mempool, is then selected by the block assembler, and causes `TestBlockValidity` to throw inside `CreateNewBlock` — stalling block production for as long as the transaction lingers (up to the mempool expiry). Layer 2 closes this by performing a height-aware rejection at mempool entry; Layer 3 provides defence in depth.

2. **CH-integrated single hard fork (original).** The cited commit positions its era at Block 630,000 (3 × halving interval). This RIP positions RIN3 at Block 840,000 (4 × halving interval) so that it activates simultaneously with the Customized Halving dilation (RIP-0002), presenting node operators and pools with a single, well-announced fork event.

3. **Scope reduction (governance decision).** The cited commit introduces a general init+overlay era table covering PoW parameters, a coinbase OP_RETURN marker, the fork tx version, and a peer-protocol floor, driven by a generated C++ header from JSON. The Core Strategic Authority (CSA) evaluated the full era system and did not adopt it. This RIP extracts only the RIN3 nVersion rule; the OP_RETURN `RIN1` branding marker is deferred (optional, no consensus impact), and the minimum peer version 70018 is tracked separately as a networking change.

   **PoW parameters are out of scope and unchanged.** The era table would render RinHash PoW parameters (Argon2d `t_cost`, `m_cost`, `lanes`, `salt`) changeable as configuration data, including a reserved `"PENDING"` salt slot for overlays not yet committed. This mechanism is not adopted. RinHash PoW parameters are consensus parameters: any change to them requires its own RIP, ratification under RIP-0001, and network adoption — the same bar as any other hard fork. Neither this RIP nor any parameter table shipped with the implementation authorises, or pre-authorises, a change to RinHash PoW parameters.

4. **Attack-simulation verification (original).** Replay-protection correctness and reorg resilience are demonstrated by dedicated simulation harnesses up to a 5,461-block (1/1000 scale) reorg that erases the entire post-CH history. See the Verification section.

5. **Peer DoS-score classification (original).** The cited commit does not address peer punishment semantics. Layer 2 rejections are classified `TX_RECENT_CONSENSUS_CHANGE` rather than `TX_CONSENSUS`, using the bucket Bitcoin Core reserves for rules newer than SegWit. With `TX_CONSENSUS`, every relay of a legacy transaction after the fork would score the relaying peer 100 points — instant discouragement. Because `recentRejects` is reset on every chain-tip change and Rincoin's block interval is 60 seconds, that filter provides only ~1 minute of repeat-suppression, so honest v1.1.0 nodes holding pre-fork mempool residue, and non-upgraded nodes passively following the post-fork chain, would be progressively disconnected from the network. The classification keeps rejection (and the Mempool Zombie DoS defence) fully intact while removing the punishment. Detachment of non-upgraded peers remains a deliberate, separately-tracked decision (minimum peer version 70018), not a side effect of transaction relay.

## Backwards Compatibility

This is a hard fork with respect to the bundled Block 840,000 event (RIP-0002 + this RIP). In isolation, the RIN3 rule narrows the block-validity set (a consensus tightening): legacy consensus places no constraint on transaction `nVersion`, so nodes that enforce Customized Halving but not RIN3 accept the post-fork chain. Before `nRinHashForkHeight`, the rule is dormant and historical blocks validate unchanged. Wallets and services that construct raw transactions MUST set `nVersion = 1380535859` for transactions intended for inclusion at or after the fork height. Coinbase, HogEx, and MWEB-only transactions are unaffected.

Non-upgraded node populations diverge in two distinct ways at Block 840,000:

- **Pre-CH implementations** (original halving schedule) reject the post-fork chain itself: the Customized Halving subsidy (4 RIN at Block 840,000) violates their expected schedule, producing a hard divergence.
- **CH-aware, RIN3-unaware implementations** (Rincoin Core v1.0.6) accept and passively follow the post-fork chain, but cannot produce acceptable blocks containing legacy-version transactions, and their wallets emit legacy-version transactions that are unmineable on the post-fork chain — such nodes can receive but not spend.

Non-upgraded nodes that passively follow the post-fork chain and relay legacy-version transactions are not discouraged at the P2P layer for doing so (§3 Layer 2); their eventual detachment is governed by the separately-tracked minimum peer version (70018), not by transaction-relay punishment.

## Security Considerations

- **Incorrect constant.** Using the wrong decimal for `RIN_FORK_TX_VERSION` produces sighash divergence on every post-fork transaction, causing a permanent chain split. Implementations MUST verify the constant is exactly `0x52494e33` = 1,380,535,859 and MUST include a test vector confirming this before deployment.

- **Mempool Zombie DoS.** Without Layer 2, a high-fee legacy-nVersion transaction stalls `CreateNewBlock` until the 14-day mempool expiry, denying block production. Layer 2 (height-aware mempool rejection) and Layer 3 (block-assembly skip) together eliminate this vector. Operators MUST deploy both layers; deploying only Layer 1 leaves the DoS window open.

- **Peer discouragement at the boundary.** Layer 2 MUST use `TX_RECENT_CONSENSUS_CHANGE`. With `TX_CONSENSUS`, a single legacy transaction relayed after the fork discourages the sending peer (score 100), and because `recentRejects` resets every 60-second tip change, the effect repeats: honest nodes with pre-fork mempool residue and non-upgraded passive followers would be severed from the P2P graph within hours of activation. The trade-off is that a peer can spam unique legacy transactions without accruing a misbehavior score; the cost is bounded by bandwidth, and the check is performed early in `PreChecks` (before signature validation), and this uses the classification Bitcoin Core reserves for post-SegWit consensus changes. Layer 1 (block-level) retains `BLOCK_CONSENSUS`: the compact-block relay path is already exempt from punishment (`via_compact_block`), and peers extending the legacy branch are disconnected regardless via `BLOCK_INVALID_PREV` on descendant blocks, so softening the block-level classification would weaken defence without protecting any honest peer.

- **Boundary race condition.** A transaction constructed at tip height `nRinHashForkHeight - 1` must already carry `RIN_FORK_TX_VERSION`, as it may be confirmed in the fork block itself. The `last_height >= fork - 1` offset in `txassembler` handles this. Wallet implementations that compute the version based on the *next* block height (rather than the tip) MUST apply the equivalent guard.

- **Exempt transaction abuse.** The exemption sets MUST be equivalent in effect: a transaction exempt at one layer MUST be exempt at every layer at which it can appear. The layers need not share a literal predicate — Layer 1 tests coinbase, HogEx, and MWEB-only explicitly, because all three can appear in a block; Layers 2 and 3 test only MWEB-only, because coinbase and HogEx transactions are rejected earlier in `MemPoolAccept::PreChecks` and therefore never reach the mempool or the block-assembly package. Implementations that relax those earlier rejections MUST restore the coinbase and HogEx tests at Layers 2 and 3.
