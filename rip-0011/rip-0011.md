## Abstract

This RIP formally documents the non-adoption of **Taproot (BIPs 340, 341, 342)** on the Rincoin mainnet, codifying the implementation change applied to `src/chainparams.cpp` in `rincoin-sim` (commit `3f3aa91`), in which the mainnet Taproot deployment is configured with BIP9 `NEVER_ACTIVE` / `NO_TIMEOUT`. The same change is pending application to Rincoin Core for v1.0.7 (see §Reference Implementation).

Unlike RIP-0004 (MWEB), which suspends activation pending a defined set of wallet-migration preconditions, this RIP proposes that Taproot **not be activated on Rincoin mainnet at all** under the current protocol family. 

The rationale combines three independent considerations: 

- (i) Divergence from Litecoin's `nMinerConfirmationWindow` that breaks the height-based activation parameters as inherited.
-  (ii) The post-activation operational pattern of Taproot on Bitcoin (Ordinals / Inscriptions) — large-scale embedding of arbitrary data in the witness section, a usage the Tapscript script-size change (BIP 342) was not designed to enable — which Rincoin's 60-second block time would amplify.
-  (iii) The limited cryptographic horizon of Schnorr signatures relative to a planned post-quantum signature transition.

Testnet and Regtest retain `ALWAYS_ACTIVE` Taproot to preserve developer tooling and upstream interoperability. This RIP is reversible by a successor RIP if the conditions in §4 change.

---

## Motivation

The mainnet Taproot deployment parameters inherited from Litecoin were:

```
DEPLOYMENT_TAPROOT.nStartHeight   = 2161152
DEPLOYMENT_TAPROOT.nTimeoutHeight = 2370816
```

Both values are aligned to Litecoin's `nMinerConfirmationWindow = 8064`. Rincoin's `nMinerConfirmationWindow` is `7920`, derived from the 60-second block time and the 33-hour `nPowTargetTimespan`:

```
nPowTargetTimespan / nPowTargetSpacing * 4
  = (33 * 3600) / 60 * 4
  = 7920
```

The inherited heights are not period-aligned under Rincoin's window:

```
2161152 % 7920 = 6912   (must be 0)
2370816 % 7920 = 2736   (must be 0)
```

Under the prior `nMinerConfirmationWindow = 8064` (the Litecoin value still carried in Rincoin Core v1.0.6), both heights are exact multiples of the window — `2161152 = 8064 × 268`, `2370816 = 8064 × 294` — so the tests passed. The misalignment is introduced specifically by the v1.0.7 correction of the window to `7920`; that correction is what caused `versionbits_sanity` and `versionbits_computeblockversion` unit-test failures during the v1.0.6 → v1.0.7 release cycle. 

The immediate fix could have been to choose new heights that are multiples of `7920`. The Rincoin Core Authority instead resolved that recompiling the height parameters without addressing the broader question of whether Rincoin should adopt Taproot at all would conflate two distinct decisions: (a) "make the inherited test pass," and (b) "commit Rincoin to Taproot's long-term operational pattern." The decision belongs in a RIP, not in a one-line numeric change.

Note on deployment fields: Rincoin's `BIP9Deployment` struct carries both BIP9 time fields (`nStartTime` / `nTimeout`) and BIP8 height fields (`nStartHeight` / `nTimeoutHeight`), all four default-initialized to `0`. Mainnet Taproot is sealed by assigning `nStartTime = NEVER_ACTIVE` and `nTimeout = NO_TIMEOUT`, and by **removing** the inherited Litecoin height assignments so that `nStartHeight` and `nTimeoutHeight` fall back to their struct default of `0`. This zeroing is mandatory, not cosmetic: `versionbits_sanity` asserts `nStartHeight == 0 && nTimeoutHeight == 0` for any `ALWAYS_ACTIVE` or `NEVER_ACTIVE` deployment, in addition to an unconditional retarget-boundary check `nStartHeight % nMinerConfirmationWindow == 0` that `0` trivially satisfies. The period-alignment invariant referenced in §4.1 / TV-4 therefore governs any future height-scheduled successor deployment, not the sealed mainnet entry, whose height fields are `0`.

## Specification

### 1. Mainnet status

The mainnet Taproot deployment in `consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT]` MUST be configured as:

```cpp
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].bit = 2;
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].nStartTime = Consensus::BIP9Deployment::NEVER_ACTIVE;
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].nTimeout = Consensus::BIP9Deployment::NO_TIMEOUT;
```

The reserved version bit `2` is held to preserve numeric parity with Litecoin and Bitcoin and to prevent inadvertent reuse for an unrelated future deployment.

Conforming Rincoin Core builds for mainnet:

- MUST NOT signal bit 2 in block headers
- MUST NOT enforce Taproot consensus rules (BIPs 340, 341, 342) on mainnet blocks
- MUST NOT relay or mine transactions that **spend** a witness v1 (Taproot) output while Taproot is inactive (`AreInputsStandard()` returns `false` for `WITNESS_V1_TAPROOT` inputs when `taproot_active == false`). By contrast, **creating** a Taproot output (`OP_1 <32-byte program>` — the script form encoded by `rin1p…` addresses under Rincoin's `rin` HRP, analogous to Bitcoin's `bc1p…`) is standard and relayable; because Taproot rules are `NEVER_ACTIVE`, such an output is anyone-can-spend at consensus, and a non-conforming miner's block creating or spending it MUST NOT cause block rejection (see TV-2).

### 2. Testnet and Regtest

Testnet and Regtest deployments retain `ALWAYS_ACTIVE` Taproot:

```cpp
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].nStartTime =
    Consensus::BIP9Deployment::ALWAYS_ACTIVE;
```

This is intentional and serves two purposes: (i) preserving upstream test vector compatibility for developers working with Bitcoin / Litecoin testnet tooling; (ii) keeping Taproot codepaths exercised in CI so that future re-evaluation under a successor RIP is not blocked by code rot.

### 3. Reserved version bit

Version bit `2` SHALL remain reserved for Taproot deployment in the `DeploymentPos` enumeration. A future RIP that proposes a different deployment for bit `2` MUST first either (i) supersede this RIP, or (ii) move Taproot's `DeploymentPos` entry to a different bit before reassignment.

### 4. Conditions under which this RIP MAY be superseded

This RIP is reversible. A successor RIP MAY propose Taproot activation if **all** of the following conditions are met:

1. **Period-aligned parameters**: The proposed `nStartHeight` and `nTimeoutHeight` are exact multiples of `nMinerConfirmationWindow` (currently `7920`), verified by adding a new `BOOST_CHECK_EQUAL` invariant to `versionbits_sanity`.

2. **Operational evidence on a peer chain**: At least one Bitcoin-family chain comparable to Rincoin in block-time and block-size policy has accumulated 24 months of post-Taproot operational data, and that data does not exhibit the data-storage usage patterns described in §"Rationale / Operational pattern" below at a rate that would consume more than 5% of Rincoin's projected block-space budget under similar adoption.

3. **Quantum-resistance positioning**: Either (a) a separate Rincoin RIP for post-quantum signature scheme adoption has reached `Active` status, eliminating the concern in §"Rationale / Cryptographic horizon"; or (b) the proposing RIP demonstrates that Taproot's introduction does not increase the migration cost of an eventual post-quantum transition.

4. **Wallet-migration completion**: SQLite descriptor-wallet migration is complete in Rincoin Core (the same precondition as RIP-0004), ensuring that Taproot output descriptors can be stored natively rather than retrofitted into BDB 4.8 wallets.

5. **Standard governance**: The successor RIP is approved per RIP-0001 Section "Version Numbering and Core Role Governance" (Founder + Core Strategic Authority).

A successor RIP that satisfies these conditions MAY supersede this RIP via the standard `Replaces` / `Superseded-By` mechanism defined in RIP-0001.

## Rationale

### Operational pattern (Ordinals / Inscriptions)

Taproot's design intent — the construction first proposed by `Gregory Maxwell` (bitcoin-dev, 2018) and specified in `(BIP 340: Wuille/Nick/Ruffing; BIPs 341–342: Wuille/Nick/Towns; 2020)` — was to provide (i) Schnorr signatures for signature aggregation, (ii) MAST for script branch privacy, and (iii) Tapscript for incremental opcode upgrades. The actual dominant post-activation usage on Bitcoin has been the embedding of arbitrary binary data in the witness section ("Ordinals" / "Inscriptions"), a use case not contemplated by the original Tapscript design, which removed the script-size limit to enable future contracting flexibility rather than bulk data storage (BIP 342).

Rincoin's protocol parameters amplify the risk of this usage pattern. At a 60-second block time, the daily block budget is 1440 blocks vs Bitcoin's ~144, increasing the block-space throughput available for data inscription by an order of magnitude under equivalent witness size limits. The Customized Halving (RIP-0002) targets a long-term security budget under the assumption that Rincoin block space is primarily consumed by monetary transactions; sustained data-inscription usage would distort that assumption.

Sealing Taproot removes the principal vector used for bulk data storage on Bitcoin since 2023 — inscription of arbitrary data in the witness section. OP_RETURN remains available, but Rincoin Core retains a conservative `-datacarriersize` default of 83 bytes as a relay-policy matter, not a consensus rule, in contrast to Bitcoin Core v30's relaxed 100,000-byte default.

### Cryptographic horizon

Both Schnorr signatures (Taproot key-path spends) and ECDSA (legacy spends) are vulnerable to Shor's algorithm on a sufficiently large quantum computer. Adopting Taproot does not materially improve Rincoin's quantum-resistance posture; it adds a signature scheme that will need to be replaced on the same timeline as ECDSA. The engineering effort required to specify, implement, test, and document a Taproot integration on Rincoin is better directed at post-quantum signature scheme research (e.g., ML-DSA / CRYSTALS-Dilithium, standardized by NIST in 2024).

### Window-size divergence

The `nMinerConfirmationWindow = 7920` value was chosen as a function of Rincoin's 60-second block time and 33-hour retarget timespan, not as a free parameter. Any consensus deployment that inherits height-based activation parameters from Litecoin requires per-deployment re-alignment under Rincoin. This RIP is the first to formalize that constraint; future Rincoin-side deployment proposals that use BIP8 height-based activation MUST verify period-alignment in `versionbits_sanity`.

### Signature aggregation (acknowledged trade-off)

The non-adoption of Taproot forgoes one objectively useful capability: Schnorr-based signature aggregation, which reduces the on-chain footprint of multisig transactions via `MuSig2` and similar protocols. Future Rincoin features that require efficient multisig (notably any multisig usage in the Cryptographic Vault / ZKP Owner Recovery design of RIP-0006) will need to specify this requirement explicitly and identify an alternative construction, such as threshold signatures or post-quantum aggregate signature schemes.

This trade-off is judged acceptable given the operational and cryptographic considerations above. The Rincoin Core Authority resolves that the cost of carrying Schnorr permanently in the protocol exceeds the benefit of one efficiency feature whose primary application (compact multisig) has not yet been demonstrated to be a load-bearing requirement in any Rincoin RIP.

### Why a RIP rather than a silent code change

Sealing Taproot in `chainparams.cpp` is a one-line implementation change. Filing it as a RIP serves three functions that the code change alone does not:

1. **Documentation**: a permanent, citable record of why mainnet Taproot is not active, available to node operators, exchanges, and future contributors who encounter the `NEVER_ACTIVE` line without context.
2. **Reversibility**: an explicit specification of the conditions under which the decision MAY be revisited (§4), preventing the silent freeze that would result from a code change alone.
3. **Governance precedent**: an example of how non-adoption decisions are handled under RIP-0001's process, distinct from the activation-style RIPs (RIP-0002, RIP-0004, etc.) that dominate the existing corpus.

## Backwards Compatibility

This RIP does not introduce a hard fork or soft fork. It documents the absence of an activation that was never deployed on Rincoin mainnet. No mainnet block has signaled or required Taproot, and no Rincoin mainnet wallet has been issued in a Taproot-derived format.

Testnet and Regtest behavior is unchanged; tooling that relies on Taproot being `ALWAYS_ACTIVE` in those environments (test vectors inherited from Bitcoin / Litecoin upstream) continues to function.

Future SegWit-style soft forks (RIP-0009 RIN3 transaction version enforcement; future BIP-equivalent deployments) are not blocked by this RIP. Version bit `2` remains reserved, and other version bits are unaffected.

## Reference Implementation

```cpp
// src/chainparams.cpp, CMainParams::CMainParams()

// Deployment of Taproot (BIPs 340-342) — RIP-0011 non-adoption
//
// Mainnet Taproot is intentionally sealed. The inherited
// Litecoin parameters (nStartHeight=2161152,
// nTimeoutHeight=2370816) are not aligned to Rincoin's
// nMinerConfirmationWindow=7920, and the Rincoin Core
// Authority has resolved that Taproot will not be activated
// on mainnet under the current protocol family. See RIP-0011
// for rationale and conditions under which this decision
// MAY be revisited.
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].bit = 2;
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].nStartTime
    = Consensus::BIP9Deployment::NEVER_ACTIVE;
consensus.vDeployments[Consensus::DEPLOYMENT_TAPROOT].nTimeout
    = Consensus::BIP9Deployment::NO_TIMEOUT;
```

Applied in commit `3f3aa91` of `rincoin-sim`. The same change is being applied to Rincoin Core for v1.0.7.

## Test Vectors

### TV-1: Mainnet Taproot signaling rejection

Under a Rincoin mainnet conforming build, mining a block with version bit 2 set:

- MUST be accepted into the chain (version bits are not consensus-enforced for non-active deployments)
- MUST NOT advance any `ThresholdState` for `DEPLOYMENT_TAPROOT`
- `VersionBitsState(pindex, params, DEPLOYMENT_TAPROOT)` MUST return `ThresholdState::FAILED` (per BIP9 NEVER_ACTIVE semantics — see `GetStateFor()` in `src/versionbits.cpp`)

### TV-2: Mainnet Taproot output standardness and spend rejection

**Output creation is standard.** A transaction whose outputs include a Taproot-format scriptPubKey (`OP_1 <32-byte program>`) submitted to a mainnet conforming node:

- IS standard and MAY be relayed and mined. `IsStandardTx()` calls `IsStandard()` on each output; `Solver()` classifies `OP_1 <32-byte>` as `WITNESS_V1_TAPROOT` (or `WITNESS_UNKNOWN`), neither of which is `NONSTANDARD`, `MULTISIG`, or oversized `NULL_DATA`, so the output is accepted. Output standardness does **not** depend on `taproot_active`.
- Because Taproot consensus rules are `NEVER_ACTIVE` on mainnet, such an output is **anyone-can-spend** at the consensus level (a witness v1 program is not evaluated under Taproot rules). Funds sent to a mainnet Taproot output are therefore unprotected.

- On mainnet (`taproot_active == false`), spending such an output is non-standard: `AreInputsStandard()` returns `false` for a `WITNESS_V1_TAPROOT` prevout via its explicit `if (!taproot_active) return false;` branch, and for a `WITNESS_UNKNOWN` prevout via the `NONSTANDARD || WITNESS_UNKNOWN` early return (the interpreter's `SCRIPT_VERIFY_DISCOURAGE_UPGRADABLE_WITNESS_PROGRAM` flag is a second, independent gate). Output *creation*, in contrast, is standard — `IsStandard()` accepts witness-program scriptPubKeys — so the consensus-level anyone-can-spend output can be mined and confirmed. This create/spend asymmetry is precisely why the send path requires the separate wallet-layer guard described in Security Considerations.

- If included in a block by a non-conforming miner, the block remains valid at the consensus level (the spend succeeds under anyone-can-spend semantics) and MUST NOT cause block rejection.

**Wallet mitigation (receive side).** The Rincoin wallet does not generate Taproot receiving addresses: `-addresstype` accepts only `legacy`, `p2sh-segwit`, and `bech32` (SegWit v0), and does not offer `bech32m` (SegWit v1 / Taproot). No mainnet wallet issues a Taproot-format address of its own, so users are not exposed on the **receive** side.

**Send side is a separate, unmitigated exposure (v1.0.7).** This does not cover sends. A user can still pay a `bech32m` (`rin1p…`) destination supplied by a third party, which constructs an anyone-can-spend output; doing so is standard wallet behavior and IS reachable. The send-side mitigation is addressed at the wallet layer (see Security Considerations, *Wallet-layer mitigation*) and is planned for v1.0.8 — it is **not** implemented in the v1.0.7 reference build.

### TV-3: Testnet Taproot acceptance

Under a Testnet or Regtest conforming build, Taproot rules are `ALWAYS_ACTIVE`. All Bitcoin / Litecoin Taproot test vectors for valid and invalid Tapscript spends MUST behave identically on Rincoin Testnet / Regtest.

### TV-4: versionbits_sanity and check_computeblockversion

`versionbits_sanity` applies two independent checks to every mainnet deployment, and the sealed Taproot entry MUST satisfy both:

```cpp
// (1) unconditional retarget-boundary check — passes because nStartHeight == 0
BOOST_CHECK_EQUAL(vDeployments[i].nStartHeight % nMinerConfirmationWindow, 0U);

// (2) sealed deployments MUST carry zero height fields
if (vDeployments[i].nStartTime == BIP9Deployment::ALWAYS_ACTIVE ||
    vDeployments[i].nStartTime == BIP9Deployment::NEVER_ACTIVE) {
    BOOST_CHECK_EQUAL(vDeployments[i].nStartHeight, 0);
    BOOST_CHECK_EQUAL(vDeployments[i].nTimeoutHeight, 0);
}
```

Check (1) is NOT skipped for `NEVER_ACTIVE`; it passes because the sealed entry's `nStartHeight` is `0`. Check (2) actively enforces that the height fields are `0`. The height-alignment path that does not run for the sealed entry lives in the separate `check_computeblockversion` test, which early-returns for `NEVER_ACTIVE` before dispatching to `check_computeblockversion_bip8` (where a height-scheduled deployment's BIP8 alignment would be exercised):

```cpp
if (nStartTime == Consensus::BIP9Deployment::NEVER_ACTIVE) return;
```

Both tests MUST pass on mainnet (NEVER_ACTIVE, height fields `0`), Testnet (ALWAYS_ACTIVE, height fields `0`), and Regtest (ALWAYS_ACTIVE, height fields `0`).

### TV-5: versionbits_computeblockversion

The full `versionbits_computeblockversion` test MUST pass under `make check` without `--run_test` exclusions, exercising the BIP8 path only via `TESTNET/DEPLOYMENT_MWEB` (the only mainnet-or-testnet height-based BIP8 deployment with period-aligned parameters at the 1/1000 simulation scale).

## Security Considerations

### No new attack surface

Non-adoption does not introduce attack surface beyond what already exists in the Rincoin codebase prior to this RIP. Taproot codepaths in `src/script/interpreter.cpp`, `src/script/sigcache.cpp`, etc., remain compiled into the binary but are not reachable on mainnet consensus paths.

### Anyone-can-spend exposure of mainnet Taproot outputs

Because mainnet Taproot is `NEVER_ACTIVE`, a witness v1 output is anyone-can-spend at the consensus level (TV-2). The wallet issues no `bech32m` receiving addresses, so users are not exposed on the receive side; however, a wallet send to a third-party-supplied `bech32m` (`rin1p…`) destination still constructs such an output. Under `NEVER_ACTIVE` this exposure is permanent, not a transient pre-activation window as it was on Bitcoin (2018–2021).

### Why no standardness filter on Taproot output creation

This RIP deliberately does NOT add a relay-policy rule to reject the creation of witness v1 outputs on mainnet, for three reasons:

1. Relay policy stricter than mining policy is ineffective and harmful: it degrades compact-block reconstruction and pressures mining centralisation when a miner includes the (consensus-valid) output anyway. This is the documented failure mode of relay-level data filtering on Bitcoin; Rincoin does not repeat it.
2. Upstream parity: Bitcoin and Litecoin treat v1 output creation as standard. Diverging increases the maintenance burden noted under "Code rot" and risks breaking the Testnet/Regtest test-vector parity that §2 preserves.
3. The protection already sits at the correct layers: `NEVER_ACTIVE` makes Taproot script-path spends non-standard (disabling the inscription reveal mechanism), and the wallet issues no `bech32m` receiving addresses.

### Wallet-layer mitigation for Taproot-destination sends (planned, v1.0.8)

The residual send-side exposure is addressed at the wallet layer, not at relay or consensus. The choke point is `CWallet::CreateTransaction`. The Rincoin codebase has no `CreateTransactionInternal`; `CreateTransaction` itself holds the guard and then delegates construction to `TxAssembler::AssembleTx`. A single guard at the top of `CreateTransaction` rejects any recipient that `Solver()` classifies as `WITNESS_V1_TAPROOT` or `WITNESS_UNKNOWN` on mainnet, and it covers both send paths: `sendtoaddress` / `sendmany` call `CreateTransaction` directly, and `FundTransaction` (`fundrawtransaction`) also calls `CreateTransaction` directly, so raw-funded outputs are inspected as well. MWEB peg-in / HogAddr outputs are unaffected because `Solver()` assigns them dedicated `WITNESS_MWEB_*` types. A fully external, self-funded transaction broadcast via `sendrawtransaction` does not pass through the wallet and is out of scope, consistent with the no-relay / no-consensus-change policy above. This mitigation is implemented in rincoin-sim on the v1.0.8 branch and is NOT part of the v1.0.7 reference build.

### Code rot

Carrying inactive Taproot code creates a maintenance burden: Bitcoin / Litecoin upstream patches to Taproot logic must still be reviewed and applied for Testnet / Regtest correctness. The Rincoin Core Authority accepts this cost as the price of testnet interoperability and reversibility (§4).

If, in a future release cycle, the maintenance burden is judged to exceed the value of preserving Testnet / Regtest Taproot, a successor RIP MAY propose full removal of Taproot codepaths. Such a successor RIP would represent a `GENERATION` or `MAJOR` change under RIP-0001 and require Founder + Core Strategic Authority unanimity.

### No precedent for silent deactivation

Rincoin mainnet has never activated Taproot. This RIP therefore does not constitute a deactivation of a previously-active consensus feature — a class of change that would carry significantly higher risk. No node, miner, or wallet operating on Rincoin mainnet has ever relied on Taproot signaling or enforcement.

### Interaction with future RIPs

- **RIP-0009 (RIN3 transaction version enforcement)**: Unaffected. RIN3 uses `nVersion` field bits, not `DEPLOYMENT_*` BIP9 bits.
- **RIP-0006 (Cryptographic Vault + ZKP)**: As noted in "Rationale / Signature aggregation," future multisig requirements in RIP-0006 must specify their own construction without assuming Schnorr availability.
- **Future post-quantum RIP (not yet numbered)**: This RIP creates the policy headroom for a post-quantum signature scheme to be the next signature-layer change on Rincoin, rather than Schnorr.

## Acknowledgments

The Taproot construction was first proposed by `Gregory Maxwell` (bitcoin-dev, January 2018); its specification is the work of `Pieter Wuille, Jonas Nick, and Tim Ruffing (BIP 340), and Pieter Wuille, Jonas Nick, and Anthony Towns (BIPs 341–342)`. The decision documented in this RIP is not a critique of that work — Taproot is appropriate for Bitcoin's design assumptions — but a recognition that Rincoin's design assumptions diverge sufficiently that the same construction does not serve the same purpose.

Litecoin's Taproot integration (David Burkett et al.) provided the inherited codebase from which Rincoin descends. The window-size divergence that originally triggered this discussion is a consequence of Rincoin's own 60-second block-time choice, not a defect in the upstream.

Identification of the `nStartHeight % nMinerConfirmationWindow` invariant violation, and the subsequent decision to escalate from a numeric fix to a non-adoption RIP, occurred during the v1.0.7 release cycle (June 2026).
