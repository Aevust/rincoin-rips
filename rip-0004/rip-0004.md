## Abstract

This RIP integrates the **MimbleWimble Extension Block (MWEB)** privacy layer into Rincoin Core and specifies a consensus-level patch to the initial **Hogwarts Express (HogEx) integration transaction** that prevents `bad-txns-vin-empty` rejection at MWEB activation.

The MWEB design is inherited from Litecoin's LIP-0002 and LIP-0003 (Andrew Yang, David Burkett, Charlie Lee, 2019) and LIP-0004 (David Burkett, 2020) with adaptations for Rincoin's RinHash Proof-of-Work algorithm and 60-second block time. Full lifecycle support (Peg-in, Peg-out, blockchain reorganization resilience) is validated against the `rincoin-sim` regtest harness.

**Operational status (mainnet)**: The Core Strategic Authority has resolved to seal MWEB activation on mainnet using the BIP9 `NEVER_ACTIVE` deployment status. Activation is not planned. Any successor RIP proposing activation MUST satisfy the mandatory conditions S-1 through S-7 of Section 2.1 - including mainnet supply-cap enforcement, a published upstream-remediation enumeration, and a 24-month upstream stability window - which are not satisfied as of this revision. This RIP preserves the full specification so that a future proposal, if ever made, does not need to re-derive the protocol design. See Section 2.1 for the rationale and conditions.

---

## Motivation

Privacy-preserving transaction layers have become a baseline expectation for sovereign monetary networks. Among the available options, MWEB provides:

- **No master keys or trusted setup**: Uses Pedersen commitments and confidential transactions natively.
- **Soft-fork compatibility**: Non-upgraded nodes continue to validate the transparent base layer without disruption.
- **Cut-through compaction**: Reduces long-term storage cost of the privacy layer compared to alternatives.

Upstream deployment history is explicitly NOT claimed by this RIP as evidence of correctness. Litecoin's MWEB has been live on mainnet since block 2,257,920 (2022-05). In 2026-03, a consensus-critical validation flaw in the block-connection path - MWEB input metadata was not fully revalidated when blocks were connected - was exploited at block 3,073,882 to produce an inflated peg-out of 85,034.47285734 LTC from an input worth no more than 1.2084693 LTC. A second exploitation attempt on 2026-04-25 was rejected by upgraded nodes but exposed a mutated-block handling defect that stalled upgraded miners, producing a 13-block invalid chain (blocks 3,095,931-3,095,943) that was later reorganized out, with confirmed third-party losses. Upstream remediation spanned Litecoin Core 0.21.5 through 0.21.5.6; the latter schedules a further MWEB soft fork at mainnet block 3,154,440 [6][7]. The re-proposal conditions in Section 2.1 are calibrated against this incident record.

However, MWEB activation introduces a non-trivial consensus consideration: at the first MWEB block, the **HogEx transaction** - the integration point between the transparent base block and the MWEB extension block - has an empty `vin` whenever that block contains no peg-ins, and is rejected by the generic `bad-txns-vin-empty` check. Upstream Litecoin does not exempt the HogEx from this check (`litecoin/src/consensus/tx_check.cpp`, verified 2026-07-11, unchanged since the v0.21 MWEB merge); upstream instead treats a peg-in-free MWEB block as invalid by design, so the extension chain opens only when the first peg-in arrives. Rincoin adopted a fork-local exemption (commit [`ecb8ad5860`](https://github.com/Aevust/rincoin-sim/commit/ecb8ad5860ff3709e0058d7602103d039cff47c7)) that admits the empty-vin HogEx.

This RIP specifies (a) the MWEB integration parameters for Rincoin, (b) the fork-local HogEx exemption and its audited properties, and (c) the scheduled retirement of that exemption at re-activation (Section 4.4).

### 2.1 Strategic suspension on mainnet

The Core Strategic Authority has resolved to suspend MWEB activation on mainnet by setting its BIP9 deployment status to `NEVER_ACTIVE`. The decision is documented here as part of the authoritative specification.

#### Rationale

1. **Wallet-migration debt**: Rincoin Core currently uses Berkeley DB 4.8 (BDB 4.8) for `wallet.dat`. The project intends to migrate to SQLite descriptor wallets, following the trajectory established by Bitcoin Core (since v0.21) and being completed by Litecoin. If MWEB were activated on mainnet under the BDB 4.8 wallet format, MWEB-specific key material (Pedersen commitment scalars, view/spend keys, output blinding factors) would be persisted in BDB-format wallets. Subsequent migration to SQLite would then require an MWEB-aware migration path that handles confidential-output state across two wallet formats - a substantially harder problem than transparent-only migration.

2. **Wait for upstream completion**: Litecoin is in the process of completing SQLite descriptor-wallet integration with MWEB support. Postponing Rincoin's mainnet MWEB activation until that integration is well-tested upstream allows Rincoin to inherit the wallet-migration design rather than develop a parallel solution.

3. **Priority on security and sustainability updates**: The protocol's security and long-run sustainability layers - RIN3 hardening and the Customized Halving schedule (RIP-0002) - take precedence over the privacy layer in the current development phase. Activating MWEB now would consume engineering resources better directed toward those layers.

4. **Upstream consensus incident record (2026)**: The 2026-03 MWEB inflation exploit and the 2026-04-25 exploit-triggered reorganization on Litecoin mainnet (see Motivation and [6]) demonstrated that the inherited MWEB codebase carried a consensus-critical inflation flaw through nearly four years of mainnet deployment, and that upstream remediation is recent and ongoing: Litecoin Core 0.21.5.6 (released 2026-08-02) schedules an additional MWEB soft fork at block 3,154,440 [7]. Activating an inherited privacy layer whose upstream is still in an active hardening cycle is incompatible with the fixed-supply guarantee (S_max, RIP-0002) that constitutes Rincoin's load-bearing protocol claim.

#### Implementation

- **Mainnet (`CMainParams`)**: The MWEB deployment in `consensus.vDeployments[Consensus::DEPLOYMENT_MWEB]` MUST be configured with `nStartTime = Consensus::BIP9Deployment::NEVER_ACTIVE` and `nTimeout = Consensus::BIP9Deployment::NO_TIMEOUT` per BIP9 conventions.
- **Testnet (`CTestNetParams`)**: MWEB MUST be configured to activate at block 840, allowing end-to-end testing of the integration without mainnet exposure.
- **Regtest (`CRegTestParams`)**: MWEB MUST be configured to activate at block 840; the `rincoin-sim` harness MUST use the same height so that 1/1000-scale results remain comparable.

No mainnet heights - neither the inherited window of Section 2 nor any other value - may be assigned to this sealed entry; `nStartHeight` and `nTimeoutHeight` fall back to their struct default of `0`. This is required, not cosmetic: `versionbits_sanity` asserts `nStartHeight == 0 && nTimeoutHeight == 0` for any `NEVER_ACTIVE` (or `ALWAYS_ACTIVE`) deployment, in addition to the unconditional `nStartHeight % nMinerConfirmationWindow == 0` check that `0` trivially satisfies.

#### Implementation status

Measured 2026-08-23 against both the v1.0.6 release and the v1.0-series `master` `src/chainparams.cpp` (deployment blocks identical): the configuration specified above is NOT yet shipped. On both, all three networks still carry Litecoin's deployment parameters verbatim (verified against Litecoin `v0.21.3`; Section 2) - mainnet `nStartHeight = 2,217,600` / `nTimeoutHeight = 2,427,264` (bit 4; source comments still reference Litecoin's 2022 calendar), testnet `nStartHeight = 2,209,536` / `nTimeoutHeight = 2,419,200`, and regtest `nStartTime = 1601450001` with `NO_TIMEOUT`. On Rincoin's 60-second block schedule the inherited mainnet window corresponds to approximately t = 4.22 to 4.61 years post-genesis; within that window, activation would additionally require 75% miner signaling (6,048 of 8,064 blocks per window), and absent such signaling the deployment times out without activating. The `NEVER_ACTIVE` seal and the block-840 testnet/regtest configuration are scheduled for the v1.1.0 consensus release; until that release ships, the inherited window remains latent in released code, and this specification-to-code delta is recorded here deliberately. Implementers MUST note that block 840 is not window-aligned on either test network (840 mod 2,016 = 840; 840 mod 144 = 120), so the block-840 activation MUST be implemented as a direct height gate rather than through `nStartHeight`.

None of the inherited values is meaningful on Rincoin's own timeline, and this is measurable rather than a matter of interpretation. Rincoin's genesis blocks carry `nTime` 1743054848 / 1743059000 / 1743059120 (2025-03-27) on mainnet / testnet / regtest. The inherited regtest `nStartTime` of 1601450001 (2020-09-30) therefore precedes Rincoin's own regtest genesis by 1,639 days, leaving that deployment window open from the first block; and the inherited mainnet and testnet heights are keyed to a block schedule whose calendar the source comments still describe in upstream terms, landing at t = 4.2 to 4.6 years on Rincoin's 60 s schedule. Verbatim inheritance is the origin of these values; it is not evidence that they were evaluated against Rincoin's parameters.

#### Conditions for re-proposal

The Core Strategic Authority's present position is that MWEB activation on Rincoin mainnet is NOT planned. This section does not describe an intended roadmap; it states what would have to be established before activation could be proposed at all. A successor RIP MUST satisfy every condition below and MUST publish the evidence for each; a condition asserted without published, reproducible evidence is unsatisfied.

**S-1 Supply integrity.** Cumulative issuance accounting MUST include MWEB peg-in / peg-out balances and MUST be machine-verifiable against S_max (168,000,000 RIN, RIP-0002). Cap enforcement in `GetBlockSubsidy()` MUST be in force on mainnet, as specified by a ratified supply-cap enforcement RIP, before activation is proposed - not concurrently with it. Rationale: the 2026 Litecoin MWEB incident was an inflation failure [6]. A privacy layer that can mint units is a monetary failure, not a privacy failure, and Rincoin's fixed supply is the load-bearing claim of the entire protocol.

**S-2 Upstream remediation gap.** Every MWEB-affecting consensus change released by Litecoin after Rincoin's fork base commit MUST be enumerated with its upstream commit hash, and each MUST be either ported or declared non-applicable with a written technical argument. The enumeration MUST be published and MUST be re-run against Litecoin HEAD at the time the successor RIP is submitted. As of this revision, the enumeration necessarily includes the Litecoin Core 0.21.5.x remediation series (0.21.5 through 0.21.5.6) [6][7]. Tag-based enumeration alone is insufficient: the public upstream repository carries no tags for the emergency releases 0.21.5 through 0.21.5.3 (measured 2026-08-25; the public tag sequence runs v0.21.4 directly to v0.21.5.4); the content of those releases is documented in [6].

**S-3 Fork-local review.** Upstream audits do NOT extend to Rincoin's fork-local divergences (the HogEx empty-vin exemption of Section 4.2, and any Rincoin-specific MWEB integration). These MUST receive independent adversarial review, published, by a reviewer with no authorship role in the code reviewed. Conversely, verbatim inheritance is not itself evidence of review: parameters and code carried over unchanged MUST be evaluated for meaningfulness under Rincoin's own genesis time, block schedule, subsidy phases, and signaling windows, not merely for byte-identity with upstream. The pre-seal deployment state documented in Section 2.1 is a worked example of this hazard on Rincoin's own networks: values that are internally consistent with upstream can still be meaningless under the fork's own parameters.

**S-4 Upstream stability clock.** MWEB MUST have been live on Litecoin mainnet for at least 48 consecutive months with no consensus-affecting MWEB incident and no emergency MWEB release on any chain deploying MWEB. Any such incident or release resets the clock to zero.

The 48-month figure is derived rather than chosen. The inflation flaw exploited in 2026-03 was present from MWEB's mainnet activation at block 2,257,920 (2022-05) until its exploitation at block 3,073,882 - approximately 46 months of uneventful mainnet operation, by calendar and by block count alike [6]. A shorter clock would accept as evidence of correctness a quiet period shorter than the demonstrated dormancy of the defect class this condition exists to guard against, which is the same reasoning error the Motivation section of this RIP identifies and removes. The value is therefore set at the observed dormancy rounded up to a whole number of years.

As of this revision (2026-08-25), the most recent qualifying events are the Litecoin Core 0.21.5.6 release (released 2026-08-02) and the MWEB soft fork it schedules at mainnet block 3,154,440 [7]. The clock therefore starts no earlier than the activation of that rule, and this condition cannot be satisfied earlier than 48 months after it. A successor RIP MUST state the clock's start height and date explicitly and MUST show that no qualifying reset event has occurred since.

**S-5 Wallet migration.** SQLite descriptor-wallet migration in Rincoin Core MUST be complete and stable for at least one full release cycle. Litecoin's SQLite + MWEB integration MUST have been the default wallet format on Litecoin mainnet - not merely available - for at least 24 months without wallet-data incidents, and the BDB -> SQLite migration path carrying MWEB state MUST have been exercised on mainnet at scale during that period. Availability without migration traffic does not satisfy this condition: a wallet created directly in SQLite never executes the migration code that this condition exists to test. For this purpose a wallet-data incident includes latent defects - MWEB outputs rendered unspendable, view or spend key material dropped, blinding factors lost - regardless of how long after the causing migration the discovery occurs. An independent audit of the BDB -> SQLite migration path, including MWEB state handling, MUST be published.

Unlike S-4, this clock is not derived from a measured incident record; no comparable public dormancy measurement exists for wallet-state migration defects, and the figure should be read accordingly. It is set longer than a single release cycle because MWEB wallet-state defects can stay latent until an old output is spent, and shorter than S-4's clock because the migration path is exercised by ordinary user activity whereas the consensus path is exercised only by attack. If a successor RIP wishes to argue for a different figure, it MUST publish the measurement it derives it from.

**S-6 Own-network validation.** Rincoin testnet MUST have validated the full peg-in / peg-out / reorg / wallet-migration lifecycle under the parameters proposed for mainnet, with published logs.

**S-7 Authority and bundling.** Ratification requires the Founder and the Core Strategic Authority jointly, per RIP-0001. The successor RIP MUST bundle the retirement of the HogEx empty-vin exemption (Section 4.4) with the re-activation deployment: `CheckTransaction` reverts to upstream Litecoin's context-free handling, under which a block containing an empty-vin HogEx is invalid, and the first MWEB block after re-activation is therefore required to contain at least one peg-in (upstream's peg-in gating). This revert is a consensus tightening (soft fork) and MUST activate at the same boundary as the re-activation deployment itself; it MUST NOT ship as a standalone release (RIP-0001 Version Authority).

If any condition is unsatisfied at the time of submission, the successor RIP MUST be rejected on procedural grounds without reaching the technical merits.

A successor RIP that satisfies every condition above MAY supersede this RIP via the standard RIP `Replaces` / `Superseded-By` mechanism defined in RIP-0001.

### 4. HogEx consensus fix

The HogEx (Hogwarts Express) transaction is the special transaction that serves as the integration commitment between the transparent block and the MWEB extension block. It appears as the **last transaction in the transparent block body** when an MWEB extension block is present.

#### 4.1 The bug

At MWEB activation height, a peg-in-free block causes the initial HogEx transaction to be rejected with `bad-txns-vin-empty` - behavior that upstream Litecoin exhibits by design (Section 4.4). This occurs because:

- The HogEx `vin` is composed of (a) the previous block's HogEx HogAddr output and (b) the current block's peg-in outputs. Peg-outs appear as HogEx *outputs*, not inputs.
- At the very first MWEB block there is no previous HogEx to spend; if that block also contains no peg-ins, the HogEx `vin` is empty.
- Stock validation logic enforces `vin.size() > 0` for all transactions except the coinbase, so this first-block HogEx is rejected with `bad-txns-vin-empty`. Upstream Litecoin retains this rejection deliberately (see Section 4.4); Rincoin's exemption admits it.

#### 4.2 The patch

Validation logic MUST distinguish HogEx transactions and apply HogEx-specific input validation rather than generic non-coinbase rules. Conforming implementations MUST:

```
IsHogExTransaction(tx, block):
    return tx == block.vtx.back()                     // last tx in block
        && block.HasMWEBData()                        // block carries MWEB extension
        && tx.HogExStructureMarker() == HOGEX_MARKER  // structural identification
        // (See LIP-0002 for HOGEX_MARKER specification)

ValidateNonCoinbaseInputs(tx, block):
    if IsHogExTransaction(tx, block):
        return ValidateHogExInputs(tx, block)         // MWEB-aware validation
    if tx.vin.empty():
        return REJECT_INVALID, "bad-txns-vin-empty"
    // ... standard validation continues ...
```

The function `ValidateHogExInputs` MUST verify that:

- The HogEx `vin` correctly references the prior MWEB extension block's commitment.
- All peg-out outputs sum to exactly the value claimed in the MWEB extension block's peg-out kernel.
- The HogEx transaction itself contributes zero net value to the transparent layer's UTXO set (peg-ins exit the transparent set; peg-outs enter it; HogEx is the accounting bridge).

The full validation specification is in LIP-0002, Section "HogEx".

> Implementation note: the reference implementation realizes this patch as a context-free exemption in `CheckTransaction` (`if (tx.vin.empty() && !tx.IsHogEx())`), keyed on the wire-recoverable `m_hogEx` flag, rather than the block-contextual identification sketched above. The positional and structural checks (last-in-block, HogAddr commitment, peg-in matching) are enforced separately in `MWEB::Node::ContextualCheckBlock` / `ConnectBlock` while MWEB is active. See Section 4.4 for the audited consequences of the context-free form.

#### 4.3 First-block edge case

At the activation block specifically, the prior block does not contain an MWEB extension. The HogEx transaction at the activation block MUST therefore be valid even when the prior MWEB state is empty (genesis-like state for the MWEB extension chain). This edge case is the specific source of the historic `bad-txns-vin-empty` failure on first activation.

Under the current revision, this edge case is handled by the fork-local exemption (Section 4.2), which is scheduled for retirement with the re-activation deployment (Section 4.4). Post-retirement, the first MWEB block MUST contain at least one peg-in, and the empty-prior-state HogEx derives its `vin` from those peg-ins - matching upstream Litecoin behavior. See Section 2.1 for the current suspension status.

#### 4.4 Divergence status and scheduled retirement (audited 2026-07-11)

The exemption specified in Section 4.2/Section 4.3 is a deliberate fork-local divergence from upstream Litecoin. An audit of the actual code paths (2026-07-11) established the following:

1. Upstream `litecoin/src/consensus/tx_check.cpp` contains no HogEx exemption (unchanged since the v0.21 MWEB merge; its only MWEB accommodation is the `!tx.IsMWEBOnly()` gate). Upstream rejects any empty-vin HogEx via the generic `bad-txns-vin-empty` check; a MWEB block with zero peg-ins is therefore invalid by design, and the extension chain does not open until the first peg-in arrives. (This audit predates the Litecoin Core 0.21.5.6 release of 2026-08-02; re-verification of this file against upstream HEAD is part of the S-2 enumeration of Section 2.1.)

2. The `m_hogEx` marker is recoverable from the wire format, so the exemption is reachable by adversarially constructed transactions (deserialization rejects only the empty-vout form). However, no inflation path exists: HogEx transactions are rejected at mempool entry, and within blocks `Consensus::CheckTxInputs` - whose ConnectBlock loop exempts only the coinbase - rejects any valued output funded by an empty vin (`bad-txns-in-belowout`). The exemption therefore admits only zero-value empty-vin HogEx transactions.

3. While MWEB is sealed `NEVER_ACTIVE` on mainnet, `MWEB::Node::ContextualCheckBlock` returns early and performs no HogEx validation. A mainnet block containing a zero-value empty-vin HogEx consequently validates under the current rules; retiring the exemption renders such a block invalid. The retirement is therefore a consensus tightening (soft fork), not a no-op, and is subject to the corresponding authority requirements of RIP-0001.

4. Because no economic incentive exists to mine such a block (it yields no value), the divergence is retained without urgency while MWEB remains sealed, and is scheduled for retirement as part of the re-activation deployment (Section 2.1). Test harnesses will then bootstrap the first MWEB block with a peg-in (mine to ACTIVE-1, submit a peg-in, mine ACTIVE), matching the verified vanilla-Litecoin regtest flow.

### 5. Peg-in transaction

A peg-in transaction:

1. Originates from a transparent address.
2. Contains exactly one output of type `OP_MWEB_PEGIN <commitment>`.
3. Has its value locked in the MWEB extension block via the HogEx accounting.

```
PEG-IN TX (transparent -> MWEB):
  vin:  standard transparent UTXO inputs
  vout: [OP_MWEB_PEGIN <commitment>]
        [optional change output, transparent]
```

---

### 6. Peg-out transaction

A peg-out transaction:

1. Originates from an MWEB address (signed via Pedersen commitment).
2. Produces an output spendable on the transparent layer.
3. Is finalized by the HogEx of the next mined block.

A 6-block confirmation depth is REQUIRED for peg-out maturity.

---

### 7. Reorganization handling

On a chain reorganization that invalidates a block containing peg-in or peg-out transactions:

- The transparent layer rolls back per standard reorg rules.
- The MWEB MMR commitments roll back to the equivalent pre-fork state.
- Peg-in commitments not yet referenced in any kernel are returned to mempool.
- Peg-out outputs that were spent on the post-fork chain are returned to MWEB UTXO set.

The full reorg semantics are inherited from LIP-0002 and validated in `rincoin-sim` (see Test Vectors below).

---

### 8. Mining policy

Mining (`generatetoaddress`) MUST direct the coinbase output to a transparent address. MWEB addresses are NOT valid coinbase recipients. This matches the Litecoin MWEB convention and is enforced at the consensus layer.

## Rationale

### Why inherit from Litecoin rather than reimplement?

MWEB is a complex consensus mechanism with subtle privacy properties. A from-scratch reimplementation would require independent cryptographic auditing of the Pedersen commitment scheme, range proof construction, kernel offset arithmetic, and MMR consistency proofs.

Inheritance is NOT justified by upstream deployment history. The 2026 incidents [6] established that upstream MWEB carried a consensus-critical inflation flaw through nearly four years of mainnet deployment (2022-05 to 2026-03): validation that existed in the mempool and block-construction paths was not fully enforced in the block-connection path. Deployment time without observed failure is therefore not accepted by this RIP as evidence of correctness - for MWEB or for any other inherited consensus subsystem.

Inheriting LIP-0002/LIP-0003 verbatim and patching only the integration points remains the lower-risk path relative to reimplementation, because it preserves the ability to port upstream remediations as they are released rather than rediscovering the same defect classes independently. That justification carries an obligation with it: tracking and porting the upstream remediation series is a precondition of any activation (Section 2.1, S-2).

### Why soft fork rather than hard fork?

The MWEB extension block design is intentionally backwards-compatible: non-upgraded nodes see only the transparent block, ignore the MWEB extension data, and continue to validate normally. This is a strict feature-add, not a rule change. Soft-fork activation imposes the lowest coordination cost on full-node operators.

### Why 75% signaling threshold (vs. 90% for RIP-0003)?

MWEB activation is consensus-additive (it adds a new transaction type without changing existing validation rules), whereas RIP-0003's CSV is consensus-modifying (it changes the subsidy schedule). The lower threshold reflects the lower coordination risk of an additive change. 75% matches Litecoin's MWEB activation threshold.

### Why block 840 on testnet / regtest?

Under the parameters inherited verbatim from the upstream codebase, the regtest activation height was an emergent artifact rather than a chosen value: regtest MWEB uses time-based BIP9 with `nStartTime = 1601450001` (2020-09-30), a date belonging to the upstream project's development timeline, which predates Rincoin's own regtest genesis (`nTime = 1743059120`, 2025-03-27), so the deployment window is open from the first block. The BIP9 state machine advances only at 144-block window boundaries (DEFINED, then STARTED, then LOCKED_IN, then ACTIVE), so with immediate full signaling the earliest possible activation falls at block 432 (3 x 144) - a height nobody selected. This emergent value, multiplied by 1,000, is the origin of the "block 432,000" figure removed from Section 2.

Block 840 replaces the emergent height with a declared one, aligned to the 1/1000-scale image of the Customized Halving boundary (block 840,000, RIP-0002), keeping Core testnet, Core regtest, and the `rincoin-sim` harness on a single deterministic activation height. Because 840 is not a multiple of either test-network signaling window, it MUST be implemented as a direct height gate (Section 2.1, Implementation status).

As of this RIP's current revision, the mainnet activation has been suspended via `NEVER_ACTIVE` per Section 2.1; any successor RIP proposing reactivation will need to select a fresh, window-aligned block height appropriate to network state at that time.

## Backwards Compatibility

This RIP defines a **soft fork** that is suspended on mainnet via `NEVER_ACTIVE` (Section 2.1). Consequences:

- **Mainnet (current state)**: MWEB consensus rules are NOT enforced. Mainnet blocks containing MWEB extension data would be rejected as malformed. Mainnet wallets MUST NOT generate MWEB-format addresses (`rinmweb1...`); attempts to send to such addresses MUST fail at the wallet layer with a clear error indicating mainnet MWEB is suspended.
- **Testnet and regtest**: The soft fork activates as specified in Section 2 and behaves per the rules below.

For the testnet/regtest activated state, the soft-fork compatibility model is:

- **Non-upgraded nodes**: Continue to validate the transparent layer correctly. They will NOT see MWEB transactions and will NOT enforce the HogEx fix. They MAY observe peg-in transactions as outputs to "unspendable" `OP_MWEB_PEGIN` scripts; these are still valid transparent transactions with valid signatures, just with outputs that the upgraded layer interprets specially.
- **Upgraded nodes**: Validate both layers. Will reject blocks where the HogEx is malformed or where MWEB extension data is inconsistent with HogEx commitments.
- **First-block hazard (historical, not currently in force on mainnet)**: The historic `bad-txns-vin-empty` rejection required that the HogEx fix be deployed in 100% of mining nodes before any mainnet activation block. This hazard does not apply under the current `NEVER_ACTIVE` state, but a successor RIP that proposes reactivation MUST address it explicitly.

The reference implementation is provided by [`rincoin-sim`](https://github.com/Aevust/rincoin-sim), specifically:

## Test Vectors (Regtest)

The following test cases MUST pass on any conforming implementation. All have been validated on `rincoin-sim` v1.0.6.1 (test date 2026-04-25).

### TV-1: Peg-In

```
GIVEN: Wallet with 13,975 RIN at transparent address rrin1q8twvefee...
WHEN:  sendtoaddress("rrmweb1qqfd6u6nk4pvyu9...", 10)
       generatetoaddress(1)
THEN:
  - Block N+1 contains 2 transactions: coinbase + peg-in TX
  - Peg-in TX outputs: [OP_MWEB_PEGIN <commitment>, transparent change ~13,975 RIN minus fees]
  - Block N+1 contains MWEB extension block with new commitment
  - HogEx transaction in block N+1 validates successfully
  - listaddressgroupings shows: rrmweb1qqfd6u6nk4pvyu9... = 10.00000000 RIN
  - listaddressgroupings shows: rrmweb1qq0mdeg9msd2hqm... = 14.99963500 RIN (auto-generated change)
```

### TV-2: Peg-Out

```
GIVEN: MWEB balance of 10 RIN at rrmweb1qqfd6u6nk4pvyu9...
WHEN:  Send 5 RIN from MWEB to a fresh transparent address rrin1...
       generatetoaddress(1)
THEN:
  - Transparent recipient receives exactly 5.00000000 RIN
  - MWEB remaining balance approximately 4.99991600 RIN (5.0 minus MWEB transaction fee)
  - HogEx transaction reflects net 5.0 RIN peg-out
```

### TV-3: Reorg Resilience

```
GIVEN: Confirmed peg-out transaction in block at height 451
WHEN:  invalidateblock(<hash of block 451>)
       Generate a dummy transaction  // ensure unique block hash
       generatetoaddress(2)            // re-mine to surpass invalidated tip
THEN:
  - After invalidate: chain tip height = 451 (one less than original 452)
  - Original peg-out TX status: 0 confirmations OR orphaned
  - After re-mine: chain tip height = 452 (matches original)
  - MWEB MMR state is consistent with re-mined block sequence
  - No double-spend of peg-out funds detected
```

### TV-4: First-block HogEx (consensus fix verification)

```
GIVEN: Chain at activation height - 1 (no prior MWEB extension)
WHEN:  Mine the first block at activation height with a HogEx referencing empty prior MWEB state
THEN:
  - Block validates successfully
  - HogEx transaction does NOT trigger bad-txns-vin-empty
  - MWEB extension block is initialized with empty UTXO set and zero kernel offset
```

> Note: TV-4 reflects the current exemption regime (Section 4.2). Upon retirement of the exemption (Section 4.4), TV-4 is superseded: the harness bootstraps the activation block with a peg-in, and a peg-in-free activation block MUST instead be rejected with `bad-txns-vin-empty`.

### TV-5: HogEx malformation rejection

```
GIVEN: Chain post-activation
WHEN:  Construct a block with malformed HogEx (e.g., peg-out total != MWEB peg-out kernel claim)
THEN:
  - Block is rejected with consensus error indicating HogEx accounting mismatch
  - Chain tip does NOT advance
```

## Security Considerations

### No precedent for silent deactivation

Rincoin mainnet has never activated MWEB. This RIP therefore does not constitute a deactivation of a previously-active consensus feature - a class of change that would carry significantly higher risk. No node, miner, or wallet operating on Rincoin mainnet has ever relied on MWEB signaling or enforcement. (Testnet / Regtest are specified to activate MWEB at block 840 per Section 2; that path is unaffected.)

### Upstream incident record (2026)

The upstream MWEB implementation suffered two consensus-affecting incidents on Litecoin mainnet in 2026: an inflation exploit at block 3,073,882 (2026-03) and an exploit-triggered 13-block invalid-chain reorganization beginning at block 3,095,931 (2026-04-25) [6]. MWEB has never activated on Rincoin mainnet, and this RIP seals mainnet activation as `NEVER_ACTIVE` (Section 2.1). Under the parameters shipped in v1.0.6 (unchanged on the v1.0-series `master` as of 2026-08-23), the inherited signaling window does not open until height 2,217,600 (approximately 4.22 years post-genesis), so neither incident class is reachable on Rincoin mainnet today; the seal removes the latent window entirely (Section 2.1, Implementation status).

Testnet and regtest are specified to activate MWEB per Section 2. Until the S-2 enumeration of Section 2.1 has been executed and applicable upstream fixes have been ported, Rincoin's MWEB code MUST be treated as unremediated with respect to the defect classes described in [6] and [7] - on every network where it is active. This fail-closed posture is acceptable for value-free test networks and is one of the reasons S-2 is a hard precondition for any mainnet proposal.

### Privacy properties

MWEB provides:

- **Confidential amounts**: Pedersen commitments hide transaction values.
- **Cut-through**: Intermediate transactions can be compacted, reducing the linkability signal.
- **Address blinding**: MWEB addresses are not directly linkable to transparent identities without explicit peg-in/peg-out reference.

MWEB does NOT provide:

- **Sender anonymity at peg-in**: A peg-in transaction is publicly visible on the transparent layer with the source transparent address.
- **Recipient anonymity at peg-out**: Similarly, the destination transparent address is visible.
- **Network-level privacy**: MWEB transactions traverse the standard P2P network with no Dandelion or Tor integration in this RIP. Network-level privacy is out of scope for this RIP and may be addressed by a future RIP.

Users MUST understand that MWEB protects in-flight value but not the perimeter (peg events).

### Activation hazard window

Under the current `NEVER_ACTIVE` mainnet configuration (Section 2.1), the activation hazard does not apply on mainnet. For testnet and regtest, the original concern remains: if soft-fork signaling fails to reach the threshold by the timeout, activation does not occur; if it reaches threshold but a non-trivial minority of mining hash power has not deployed the HogEx fix, the activation block is at risk of producing chain splits. Coordinated deployment is the operational responsibility of mining pool operators on those networks.

A successor RIP that proposes lifting the `NEVER_ACTIVE` suspension on mainnet MUST address the activation hazard window explicitly, including specifying mining-pool readiness verification before the activation block is reached.

### Reorg double-spend window

During a reorg that affects peg events, there is a brief window in which a peg-out output may be spent on both the original and the re-mined chain (until the HogEx-level accounting reconciles). The 6-block peg-out maturity requirement is intended to ensure this window is closed before peg-out funds are usable.

### Cryptographic dependencies

MWEB relies on the discrete logarithm assumption over secp256k1 (for Pedersen commitments) and on the soundness of the bulletproof range proof scheme. These dependencies are inherited from Litecoin's MWEB and from the broader Bitcoin cryptographic stack. A break of either would compromise both Rincoin's MWEB and a substantial portion of the cryptocurrency ecosystem.

### Legacy address quarantine interaction

When the Cryptographic Vault and Phased Legacy Address Migration mechanisms (RIP-0006, RIP-0008) eventually deprecate legacy elliptic curve cryptography, MWEB outputs MUST also undergo the migration. The migration of MWEB UTXOs is non-trivial because the Pedersen commitments themselves rely on EC primitives. Detailed handling is deferred to RIP-0008 and any future MWEB-specific migration RIP.
